# ADR-0002: Drizzle ORM and PGlite instead of Prisma

- **Status:** Accepted (amends ADR-0001 §3)
- **Date:** 2026-11-03

## Context

ADR-0001 chose Prisma (familiar from EmlakPro). While building the API we
wanted two things Prisma makes awkward:

1. **No database to install for development and tests.** Contributors and CI
   should run the full API, including row-level security, without a
   PostgreSQL server.
2. **SQL-first control** for the security model: forced row-level security
   policies, per-transaction `set_config('app.family_id', …)`, and a
   non-superuser role in tests.

## Decision

- Use **Drizzle ORM** with SQL migrations generated by drizzle-kit
  (`apps/api/migrations`), plus a hand-written migration for RLS
  (`0001_rls.sql`).
- Use **PGlite** (PostgreSQL compiled to WASM, in-process) for development
  and tests; **node-postgres** in production. One code path (`db/client.ts`).
- In PGlite the app switches to a non-superuser role after migrating, so RLS
  is enforced exactly as in production. In production the API refuses to start
  as a superuser or a BYPASSRLS role.
- Better Auth uses its Drizzle adapter.

## Consequences

- Tests run real PostgreSQL semantics (constraints, RLS) in ~6 s with no setup.
  A mutation check showed 8 isolation tests fail if RLS is bypassed.
- `drizzle-orm` is listed at the repo root as well, so `drizzle-kit` (hoisted
  there) can resolve it.
- Prisma experience from EmlakPro doesn't transfer directly; Drizzle's query
  builder is close to SQL and small.
